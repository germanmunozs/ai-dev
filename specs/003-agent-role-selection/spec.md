# Feature Specification: Agent Role Selection

**Feature Branch**: `003-agent-role-selection`

**Created**: 2026-09-28

**Status**: Draft

**Input**: User description: "Introduce agent selection by development role. Given an explicitly requested development role, determine which supported coding agent (from the 002-coding-agent-execution registry of canonical agent identities) ai-dev should select for it, and report that result to a human or automated caller. A development role (e.g., specification, planning, implementation, review, remediation) is a distinct domain concept from a coding agent; the generic role-selection model must stay vendor-neutral and must not leak Claude Code or Codex CLI concepts into it. Selection must be deterministic, read-only with respect to agents, and must not execute, launch, authenticate, or reconfigure any coding agent. The feature stops at role -> select -> report; it explicitly excludes execution as a consequence of selection, automatic SDD workflow execution, chained or fallback agents, multi-agent conversations, dynamic/LLM-based/probabilistic routing, scoring, persistent workflow state, and any future orchestration engine. The human must explicitly request a role selection; ai-dev must never independently decide that a development activity should occur."

## Clarifications

### Session 2026-09-28

- Q: What is the minimum development-role set this feature should define? → A: All five roles given as examples in the feature brief: specification, planning, implementation, review, and remediation. This set maps directly to the constitution's mandated Specification → Plan → Tasks → Implementation workflow plus its review and remediation quality-gate concerns.
- Q: When a role maps to a supported agent, must selection require that agent to be locally available right now, or just identify the configured/preferred agent regardless of availability? → A: Selection must require the mapped agent to be locally available at the time of the request. If the mapped agent is not locally available, the request does not resolve to a selected agent; it produces a distinct failure outcome instead.
- Q: Is the role-to-agent mapping something a human can view or change in this feature, or a fixed built-in default? → A: The mapping is a fixed, built-in default for this feature. This feature does not provide a capability to view, edit, persist, override, score, or dynamically configure the mapping independently of requesting a selection; that remains a possible future feature.
- Q: What is the complete fixed built-in role-to-agent mapping for this feature? → A: specification → `claude-code`; planning → `claude-code`; implementation → `codex-cli`; review → `claude-code`; remediation → `codex-cli`. This is the complete, observable, fixed built-in selection policy for this feature. It does not indicate that either supported agent is inherently better suited to any role; role semantics remain independent of agent identity.
- Q: Must `selection_inconsistent` serve as a general-purpose or catch-all outcome for any internal error the system encounters while processing a selection request? → A: No. `selection_inconsistent` is strictly an integrity-failure outcome reserved for a mismatch between the fixed mapping's target agent identity and the supported-agent registry. It must not be produced for parsing errors, output-format errors, agent-availability failures, discovery-implementation errors, report-generation errors, or any other internal error unrelated to a mapping/registry mismatch. Under the mapping above together with the supported-agent registry defined in 002-coding-agent-execution, this condition does not occur in normal operation.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Determine which agent is selected for a role that is ready to use (Priority: P1)

A developer has decided which kind of development activity they are about to do (for example, "I'm about to write a specification") and wants to know, without running anything, which supported coding agent `ai-dev` would use for that kind of activity right now.

**Why this priority**: This is the entire purpose of the feature: turning an explicit human decision about a development role into an observable, reportable agent identity. Every other behavior in this feature exists to make this core answer trustworthy.

**Independent Test**: Can be fully tested by requesting selection for a recognized development role whose mapped agent is supported and currently locally available, and confirming the report names exactly that agent's canonical identity, reports a success outcome, and that no agent process is invoked as a result.

**Acceptance Scenarios**:

1. **Given** a recognized development role (for example, implementation) whose mapped canonical agent is supported and currently locally available, **When** the developer explicitly requests selection for that role, **Then** `ai-dev` reports outcome `role_selected` together with the mapped agent's canonical identity, and does not invoke any agent process.
2. **Given** the same setup, **When** the developer repeats the identical selection request without any change to local supported-agent state, **Then** the second report is identical to the first in outcome and selected agent identity.
3. **Given** a recognized role whose mapped agent is available, **When** the developer requests selection in machine-readable mode, **Then** the machine-readable report exposes the requested role, the selected canonical agent identity, and the outcome value without requiring the reader to parse free-form text.
4. **Given** all five recognized development roles, **When** the developer requests selection for each one individually, **Then** each request is resolved independently to its own mapped agent identity, and none of the requests execute, depend on, or chain into any other role's selection.
5. **Given** a completed `role_selected` request, **When** the developer inspects the local repository and filesystem afterward, **Then** no content was created, modified, or deleted as a result of that request.
6. **Given** the fixed mapping defined for this feature, **When** a developer inspects the mapping's five entries, **Then** the mapping is exactly: specification → `claude-code`, planning → `claude-code`, implementation → `codex-cli`, review → `claude-code`, remediation → `codex-cli`, and no capability exists in this feature to view, edit, persist, override, score, or dynamically configure it.

---

### User Story 2 - Understand clearly when a requested role is not recognized (Priority: P2)

A developer names a development role that is misspelled, invented, or otherwise not part of the roles `ai-dev` recognizes, and needs to know immediately and unambiguously that the role itself was not recognized, rather than receiving a selection result that looks valid.

**Why this priority**: A silently accepted but meaningless role would be worse than no answer at all, since a human or automated caller could act on a fabricated selection. This is prioritized after the core success path because it is a correctness guard on requests that never had a valid role to begin with.

**Independent Test**: Can be fully tested by requesting selection using a role name outside the recognized role set and confirming a distinct "unsupported role" outcome is reported, with no agent identity present and no availability check performed.

**Acceptance Scenarios**:

1. **Given** a role name that is not one of the five recognized development roles, **When** the developer requests selection with that name, **Then** `ai-dev` reports outcome `role_unsupported`, includes no selected agent identity, and does not check any agent's local availability.
2. **Given** no role value supplied at all, **When** the developer invokes the selection capability, **Then** `ai-dev` reports a usage failure distinct from `role_unsupported`, emits no role-selection report, and completes unsuccessfully.
3. **Given** a role value consisting only of whitespace, **When** the developer requests selection with that value, **Then** `ai-dev` treats it as a missing role (a usage failure), not as `role_unsupported`.
4. **Given** a syntactically valid selection request naming a role value outside the five canonical roles, **When** `ai-dev` reports `role_unsupported`, **Then** the machine-readable report exposes the originally supplied role value exactly as given, but exposes no canonical requested role (none exists for this outcome), no selected agent identity, and no mapped agent identity.

---

### User Story 3 - Understand clearly when a recognized role's mapped agent cannot currently be used (Priority: P3)

A developer requests selection for a development role that `ai-dev` does recognize, but the coding agent that role maps to is not currently usable on this machine, and needs to know that plainly instead of receiving a selection that would not actually work.

**Why this priority**: Because selection requires the mapped agent to be locally available to succeed, the human needs equally explicit signaling when that condition is not met, distinct both from an unrecognized role and from a successful selection. It is prioritized after the core success and unsupported-role paths because it addresses a state-dependent condition of an otherwise-valid request.

**Independent Test**: Can be fully tested by requesting selection for a recognized role whose mapped agent is a supported but locally unavailable coding agent, and confirming the report shows a distinct "agent unavailable" outcome (not `role_selected`, not `role_unsupported`), naming both the requested role and the unavailable mapped agent's identity.

**Acceptance Scenarios**:

1. **Given** a recognized development role whose mapped agent is a supported coding agent that is not currently locally available, **When** the developer requests selection for that role, **Then** `ai-dev` reports outcome `agent_unavailable`, names the requested role and the mapped agent's canonical identity, reports no selected agent identity, and does not invoke any agent process.
2. **Given** a controlled test configuration in which the supported-agent registry does not include an agent identity that the fixed mapping designates for a given role (a condition constructed for test purposes, independent of whether the approved production mapping in FR-003 is itself ever invalid), **When** the developer requests selection for that role under that test configuration, **Then** `ai-dev` reports outcome `selection_inconsistent`, names the mapping-target identity separately from any selected agent, and reports no selected agent identity.
3. **Given** any failure outcome (`role_unsupported`, `agent_unavailable`, or `selection_inconsistent`), **When** the developer reads the report, **Then** it never resembles or could be mistaken for `role_selected`, and the command reports unsuccessful completion.
4. **Given** an internal error unrelated to a mapping/registry mismatch (for example, a defect while generating the report, or a failure while performing agent-availability discovery), **When** that error occurs, **Then** `ai-dev` MUST NOT report `selection_inconsistent` for it; `selection_inconsistent` is reserved exclusively for a mismatch between the fixed mapping's target agent identity and the supported-agent registry.
5. **Given** any outcome other than `role_selected` (`role_unsupported`, `agent_unavailable`, or `selection_inconsistent`), **When** the request completes, **Then** `ai-dev` has not attempted another agent, chosen an alternate agent, retried selection with another mapping, or executed any agent for that request; a subsequent attempt requires a new explicit human request.

---

### Edge Cases

- What happens when the requested role differs from a recognized role identifier only in letter case (for example, "Implementation" instead of "implementation")? Role matching is exact against the recognized role identifiers; a non-matching case is reported as `role_unsupported`.
- What happens when extra positional arguments or unrecognized options are supplied alongside an otherwise valid role? `ai-dev` reports a usage failure, invokes no role-selection logic, emits no role-selection report, and completes unsuccessfully.
- What happens when the same role selection request is issued concurrently in multiple processes? Each request is independent; this specification does not require any coordination or locking between concurrent invocations.
- What happens when the local availability of the mapped agent changes between two selection requests for the same role? Each request reflects the supported-agent state at the time of that request; determinism (see Requirements) applies only when that state is unchanged between requests.
- What happens when a future development role is added to the recognized role set? Existing roles' mappings and outcomes are unaffected; the new role behaves like any other recognized role once it exists.
- What happens when a future coding agent is added to the supported-agent model? It becomes eligible to appear as a mapped agent for whichever roles the built-in default mapping assigns to it; already-defined mappings for other roles are unaffected.
- What happens when the fixed default mapping for a recognized role points to a coding agent identifier that does not exist in the current supported-agent model (for example, after a supported agent is removed in a future version)? `ai-dev` reports `selection_inconsistent` rather than treating it as an ordinary unavailable-agent case, signaling an internal mapping defect distinct from an environment-availability issue.
- What happens when a developer expects role selection to also run the selected agent? Selection never executes, launches, or authenticates any agent regardless of outcome; running the selected agent, if desired, requires a separate, explicit action through the execution capability defined in 002-coding-agent-execution.
- What happens when a role selection request produces any outcome other than `role_selected`? `ai-dev` takes no further automatic action for that request: it does not try another agent, choose an alternate agent, retry selection with another mapping, or execute any agent. The request ends at reporting; a subsequent attempt requires a new explicit human request.
- What happens to repository or filesystem content as a result of a role selection request, regardless of outcome? Nothing is created, modified, or deleted; selection is observational/read-only with respect to both external coding agents and local project content.
- What happens to the existing behavior of `ai-dev agents` (listing) and `ai-dev agent run` (execution) as a result of this feature existing? Their approved observable behavior, as defined in 002-coding-agent-execution, is unchanged; this feature reuses, and does not redefine, the existing meanings of canonical agent identity, supported agent, and local availability.
- What happens when an internal error occurs that is unrelated to a mismatch between the fixed mapping and the supported-agent registry (for example, a defect in report generation or in agent-availability discovery)? `ai-dev` does not report `selection_inconsistent` for it; that outcome is reserved exclusively for a mapping-target identity absent from the supported-agent registry, and is not a catch-all for other internal errors.
- What happens when the concrete fixed mapping (specification → `claude-code`, planning → `claude-code`, implementation → `codex-cli`, review → `claude-code`, remediation → `codex-cli`) is read as a claim about agent quality? It is not: the mapping is a fixed built-in default only, and role semantics remain independent of agent identity.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST provide a capability through which a human explicitly requests selection of exactly one development role.
- **FR-002**: The system MUST recognize exactly five development roles for this capability: specification, planning, implementation, review, and remediation. A development role is a distinct domain concept from a coding agent and MUST NOT be defined in terms of any specific coding agent's vendor, product name, or implementation. A supplied role value MUST be matched exactly and case-sensitively against these five identifiers; the system MUST NOT apply normalization, aliasing, abbreviation, or fuzzy matching to a supplied role value.
- **FR-003**: The system MUST maintain the following fixed, built-in, deterministic mapping from each recognized development role to exactly one canonical coding agent identity drawn from the supported-agent model defined in 002-coding-agent-execution:

  | Development Role | Mapped Canonical Agent Identity |
  |---|---|
  | specification | `claude-code` |
  | planning | `claude-code` |
  | implementation | `codex-cli` |
  | review | `claude-code` |
  | remediation | `codex-cli` |

  This mapping MUST be a fixed built-in default for this feature. The system MUST NOT provide any capability to view, edit, persist, override, score, or dynamically configure this mapping. The existence of this mapping MUST NOT be represented, described, or documented as evidence that one supported coding agent is inherently better suited than another for any role; development-role semantics remain independent of coding-agent identity.
- **FR-004**: The system MUST NOT execute, launch, authenticate, or otherwise invoke any coding agent as a result of a role selection request, regardless of the request's outcome. Role selection is strictly read-only with respect to coding agents.
- **FR-005**: The system MUST determine the mapped agent's availability for a role selection request using the same local-availability determination used by the supported-agent model in 002-coding-agent-execution: locally discoverable at the time of the request. This determination MUST NOT assert or require authentication or network reachability.
- **FR-006**: When the requested development role is recognized and its mapped agent is a supported coding agent that is currently locally available, the system MUST report outcome `role_selected` together with the requested role and the mapped agent's canonical identity.
- **FR-007**: When command syntax constitutes a recognized Role Selection Request (see Key Entities) and the supplied role value is not one of the five canonical development roles, the system MUST report outcome `role_unsupported`. This outcome MUST report the originally supplied role value exactly as given, MUST NOT report any canonical requested role (none exists for this outcome), MUST NOT report any selected agent identity, MUST NOT report any mapped agent identity, and MUST NOT attempt any agent availability check.
- **FR-008**: When the requested development role is recognized and its mapped agent is a supported coding agent that is not currently locally available, the system MUST report outcome `agent_unavailable`, identify both the requested role and the mapped agent's canonical identity, MUST NOT report any selected agent identity, and MUST NOT report `role_selected`.
- **FR-009**: When the requested development role is recognized but its fixed mapping (FR-003) references a coding agent identity that is not part of the current supported-agent model (see 002-coding-agent-execution), the system MUST report outcome `selection_inconsistent` rather than `role_selected` or `agent_unavailable`. This outcome MUST identify the mapping-target agent identity separately from any selected agent, and MUST NOT represent that identity, or any other identity, as a selected agent. `selection_inconsistent` is strictly an integrity-failure outcome for a mismatch between the fixed mapping and the supported-agent registry; it MUST NOT be produced for, and MUST NOT serve as a catch-all for, parsing errors, output-format errors, agent-availability failures, discovery-implementation errors, report-generation errors, or any other internal error unrelated to a mapping/registry mismatch. Under the mapping defined in FR-003 together with the supported-agent registry defined in 002-coding-agent-execution, this outcome does not occur in normal operation; it is exercised only under a deliberately controlled mismatch condition (see User Story 3, Acceptance Scenario 2).
- **FR-010**: Every role selection outcome the system reports for a recognized request MUST be exactly one of: `role_selected`, `role_unsupported`, `agent_unavailable`, or `selection_inconsistent`. No outcome may be ambiguous between these, and no failure outcome may be presented in a way that resembles or could be mistaken for `role_selected`.
- **FR-011**: For identical requested role, fixed mapping (FR-003), supported-agent registry, and local availability state, the reported outcome and the selected canonical agent identity (when applicable) MUST be identical across repeated requests. The system MUST NOT use scoring, ranking, randomness, prompt-based inference, learning, dynamic routing, or any other nondeterministic mechanism to choose or report a mapped or selected agent.
- **FR-012**: The system MUST provide an explicitly selectable machine-readable report for a role selection request, in addition to a human-readable presentation, consistent with the pattern established by 002-coding-agent-execution. The machine-readable report MUST expose, without requiring the reader to parse free-form text and without introducing unnecessary serialization detail:
  - the role value exactly as originally supplied;
  - the canonical requested role, when the supplied value matches one of the five recognized roles (absent for `role_unsupported`, per FR-007);
  - the selected canonical agent identity, when the outcome is `role_selected` (absent otherwise);
  - the mapped or target agent identity, when required by the outcome's semantics (the mapped agent's canonical identity for `agent_unavailable` per FR-008; the unsupported mapping-target identity for `selection_inconsistent` per FR-009; absent for `role_selected` and `role_unsupported`);
  - exactly one stable outcome value from FR-010.
- **FR-013**: The system MUST require a separate, explicit human-initiated request to produce a role selection result. The system MUST NOT infer, perform, or trigger a role selection as a side effect of any other capability, and MUST NOT independently decide that a specification, planning, implementation, review, or remediation activity should occur.
- **FR-014**: For a request to be syntactically recognized as a Role Selection Request, the system MUST require exactly one supplied, non-empty role value. This supplied role value MAY be either one of the five canonical development roles or an unsupported role value (per FR-007); the system MUST NOT require the supplied value to be canonical for the request to be syntactically recognized. The system MUST NOT accept multiple role values in a single request and MUST NOT chain, combine, or aggregate selection results across roles.
- **FR-015**: When no development role is supplied, or when command syntax or options cannot be parsed into a recognized selection request (for example, extra arguments or invalid option format), the system MUST treat this as a usage failure outside the role-selection-outcome model: it MUST report the usage problem, MUST NOT attempt any role selection or availability check, MUST NOT emit a role-selection report, MUST NOT launch or invoke any coding agent, and MUST complete unsuccessfully.
- **FR-016**: When the supplied role value is empty or consists only of whitespace, the system MUST treat it as a missing role (a usage failure per FR-015), not as `role_unsupported`.
- **FR-017**: The command process reporting a role selection request MUST report successful completion if and only if the outcome is `role_selected`, and MUST report unsuccessful completion for `role_unsupported`, `agent_unavailable`, `selection_inconsistent`, or any usage failure; a usage failure's unsuccessful completion MUST occur without emitting any role-selection report (per FR-015). This specification does not introduce or require any implementation-specific numeric exit code beyond what an existing, already-approved ai-dev compatibility contract requires.
- **FR-018**: Adding a new supported coding agent to the supported-agent model MUST NOT require redefining the meaning, recognized set, or selection semantics of any development role.
- **FR-019**: Adding a new development role to the recognized role model MUST NOT alter the mapping, meaning, or selection semantics of any already-recognized development role.
- **FR-020**: The system MUST NOT alter, elevate, or otherwise change any coding agent's permissions, sandbox configuration, approval behavior, or authentication state as part of a role selection request.
- **FR-021**: The system MUST NOT perform network probes or reachability checks as part of determining agent availability for role selection; availability determination MUST rely only on local discoverability, consistent with 002-coding-agent-execution.
- **FR-022**: The system MUST NOT introduce, append, or expose any credential, token, secret, or other sensitive environment value in any role selection output it produces.
- **FR-023**: For any role selection request whose outcome is not `role_selected`, the system MUST take no further automatic action for that request: it MUST NOT attempt another agent, choose an alternate agent, retry selection using another mapping, or execute any agent. Each such request ends at reporting; a subsequent attempt requires a new, separate, explicit human request.
- **FR-024**: The system MUST NOT create, modify, or delete any repository or filesystem content as part of processing a role selection request, regardless of outcome. Role selection MUST remain observational and read-only with respect to both external coding agents and local project content.
- **FR-025**: This feature MUST NOT change the approved observable behavior of the existing coding-agent listing capability or the existing coding-agent execution capability defined in 002-coding-agent-execution. This feature MUST reuse, and MUST NOT redefine, the existing meanings of canonical agent identity, supported agent, and local availability established by 002-coding-agent-execution.
- **FR-026**: This feature MUST implement role selection strictly as role → select → report. It MUST NOT execute a selected agent as a consequence of selection, and MUST NOT implement routing, scoring, automatic retries, fallback, chained agent invocations, persistent workflow state, automatic SDD phase selection, automatic remediation triggering, dynamic plugin loading, MCP orchestration, authentication management, or any mapping-management capability.
- **FR-027**: Every human-readable presentation of a recognized role selection result MUST visibly display the exact canonical outcome value (`role_selected`, `role_unsupported`, `agent_unavailable`, or `selection_inconsistent`) required by FR-010. This requirement governs only that the exact value is visibly present; it does not prescribe surrounding cosmetic formatting.

### Key Entities

- **Development Role**: A named category of development activity a human may explicitly request selection for. The recognized set for this feature is fixed: specification, planning, implementation, review, and remediation. A Development Role is a domain concept independent of any coding agent; adding a future role does not change the semantics of already-recognized roles. Matching a supplied role value against this set is exact and case-sensitive, with no aliasing or normalization.
- **Selection Policy**: The fixed, built-in, deterministic association between each recognized Development Role and exactly one canonical coding agent identity drawn from the supported-agent model. Concretely: specification → `claude-code`, planning → `claude-code`, implementation → `codex-cli`, review → `claude-code`, remediation → `codex-cli` (FR-003). Not human-viewable, editable, persistable, overridable, scorable, or dynamically configurable within this feature. This association does not imply that either mapped agent is inherently better suited to any role; role semantics remain independent of agent identity.
- **Role Selection Request**: A syntactically valid, human-initiated request naming a single role value (and, optionally, other recognized selection options such as an output-format choice). A Role Selection Request's syntactic validity is independent of whether its role value is one of the five canonical Development Roles: the same request shape may carry either a canonical role or an unsupported role value. A request that cannot be syntactically recognized as such — for example, a missing role value, a whitespace-only role value, extra positional arguments, an unknown option, or an unsupported output-format value — is a usage failure (FR-015), not a Role Selection Request.
- **Role Selection Outcome**: The result of one recognized Role Selection Request: the originally supplied role value; the canonical requested role, when the supplied value is one of the five Development Roles (absent for `role_unsupported`); the selected canonical agent identity, present only when the outcome is `role_selected`; the mapped or target agent identity, present only when the outcome is `agent_unavailable` or `selection_inconsistent`; and exactly one stable outcome value (`role_selected`, `role_unsupported`, `agent_unavailable`, or `selection_inconsistent`) — presented in both human-readable and machine-readable form.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A developer can determine, with a single request and without invoking or launching any coding agent, which supported coding agent (if any) is currently selected for a given development role.
- **SC-002**: Across all five recognized development roles, 100% of selection requests made against unchanged supported-agent state produce identical outcomes and, when applicable, identical selected agent identities across repeated invocations.
- **SC-003**: 100% of syntactically recognized Role Selection Requests whose supplied role value is outside the five canonical development roles produce the canonical `role_unsupported` outcome and never report a selected agent identity.
- **SC-004**: 100% of requests for a recognized role whose mapped agent is not locally available report `agent_unavailable` rather than `role_selected` or any other outcome.
- **SC-005**: 0% of role selection requests, regardless of outcome, result in any coding agent process being launched, authenticated, or otherwise invoked.
- **SC-006**: An automated caller can determine, from the machine-readable report alone and without parsing free-form text, the originally supplied role value, the canonical requested role when one exists, the selected canonical agent identity when the outcome is `role_selected`, the mapped or target agent identity when the outcome is `agent_unavailable` or `selection_inconsistent`, and the exact outcome value of any role selection request.
- **SC-007**: Support for a new coding agent or a new development role can be added and verified against this specification's acceptance criteria without changing the observable selection outcome of any already-recognized role under unchanged supported-agent state.
- **SC-008**: 100% of role selection requests whose outcome is not `role_selected` result in zero subsequent automatic agent attempts, alternate-agent selections, mapping retries, or agent executions for that same request.
- **SC-009**: 0% of role selection requests, regardless of outcome, result in any repository or filesystem content being created, modified, or deleted; and 100% of existing acceptance scenarios for the coding-agent listing and coding-agent execution capabilities defined in 002-coding-agent-execution remain unchanged in observable behavior after this feature is present.
- **SC-010**: Under a controlled test condition constructing a mismatch between the fixed mapping's target agent identity and the supported-agent registry, 100% of selection requests for the affected role report `selection_inconsistent`; under the approved production mapping (FR-003) together with the supported-agent registry defined in 002-coding-agent-execution, 0% of selection requests report `selection_inconsistent`.

## Assumptions

- The five recognized development roles (specification, planning, implementation, review, remediation) constitute the complete recognized role model for this feature; this reflects an explicit human decision made during specification of this feature.
- Selection requires the mapped agent to be locally available at request time to succeed; a recognized role whose mapped agent is supported but not currently locally available produces `agent_unavailable`, not `role_selected`. This reflects an explicit human decision made during specification of this feature.
- The role-to-agent selection mapping is a fixed, built-in default for this feature: specification → `claude-code`, planning → `claude-code`, implementation → `codex-cli`, review → `claude-code`, remediation → `codex-cli` (FR-003). This exact mapping reflects an explicit human decision made during specification of this feature and is not evidence that either mapped agent is inherently better suited to any role. A capability for a human to view, edit, persist, override, score, or dynamically configure the mapping independently of a selection request is out of scope and may be addressed by a future feature.
- `selection_inconsistent` is reserved exclusively for a mismatch between the fixed mapping's target agent identity and the supported-agent registry; it is not a catch-all for parsing, output-format, availability, discovery-implementation, or report-generation errors. Under the approved mapping and the current 002-coding-agent-execution supported-agent registry, this condition does not occur in normal operation.
- This specification does not introduce or require any implementation-specific numeric exit code beyond what an existing, already-approved ai-dev compatibility contract requires.
- This feature does not change the approved observable behavior of the existing coding-agent listing or coding-agent execution capabilities defined in 002-coding-agent-execution, and reuses rather than redefines their existing meanings of canonical agent identity, supported agent, and local availability.
- This feature implements strictly role → select → report; it does not implement role → select → execute, and introduces no routing, scoring, retries, fallback, chained agents, workflow state, automatic SDD phase selection, automatic remediation, dynamic plugins, MCP orchestration, authentication management, or mapping-management capability.
- Availability for role selection reuses the same local-discoverability definition established by 002-coding-agent-execution; it does not assert authentication or network reachability, and a prior availability result is only a point-in-time discovery result.
- Role identifiers are matched exactly (case-sensitive) against the five recognized role names; no implicit normalization, abbreviation, or fuzzy matching is performed.
- This specification does not require or define any persistence of past selection requests or outcomes between invocations; each request is independent.
- This specification does not define or perform agent execution as a consequence of selection; see 002-coding-agent-execution for execution semantics. A future feature may combine role selection with execution.
- The command syntax illustrated in discussion of this feature (conceptually resembling `ai-dev agent select <role>`) is illustrative only; exact command syntax, programming language, CLI framework, and machine-readable serialization format are implementation/plan concerns, left open as long as the observable behavior defined here is satisfied, consistent with 002-coding-agent-execution.
- A standalone capability to list or enumerate the recognized role set independently of requesting a selection is out of scope for this feature.
