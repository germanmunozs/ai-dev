# Feature Specification: Workflow State

**Feature Branch**: `004-workflow-state`

**Created**: 2026-09-30

**Status**: Draft

**Input**: User description: "Feature: Workflow State. ai-dev needs a vendor-neutral workflow-state capability that can represent and report the current lifecycle state of a software-development feature. The purpose of this feature is to establish the domain model and observable contract for workflow state so later features can build SDD workflow orchestration and explicit Human Gates on top of it. Context: Feature 001 established environment/repository diagnostics. Feature 002 established explicit coding-agent execution and its execution outcomes. Feature 003 established deterministic development-role selection for: specification, planning, implementation, review, and remediation. Workflow state must remain conceptually separate from agent execution, agent availability, role selection, and future Human Gate approval. An agent reporting success must never by itself imply workflow approval or authorization to advance to another state. Human authority must be preserved. Define the smallest useful workflow-state capability. Keep the feature vendor-neutral. Do not assume or introduce automatic coding-agent execution, automatic role selection, routing/retry/fallback/chaining, SDD phase orchestration, Human Gate implementation, automatic approval, review/remediation loops, background execution, plugins or MCP orchestration, authentication or network-readiness management, permission/sandbox/approval bypasses, Git branch/merge/release automation, or an interactive/TUI workflow, unless required by an explicitly clarified product decision. Define observable behavior and product requirements, not implementation architecture."

## Clarifications

### Session 2026-09-30

- Q: Should 004 only evaluate and report the current workflow state and transition validity, or should it also let a human explicitly apply (persist) a state transition? → A: Evaluate and report only. This feature is purely observational: it reports current state and evaluates whether a hypothetical transition would be valid, but never writes or persists any state itself. It has zero filesystem side effects and mirrors 003's strictly read-only precedent; a later feature will own actually applying and persisting transitions.
- Q: What canonical state vocabulary should this feature define for a feature's workflow lifecycle? → A: SDD lifecycle phases: `draft` -> `specified` -> `planned` -> `tasked` -> `implemented`, plus a terminal `approved` state and a terminal `abandoned` state reachable from any non-terminal state. This mirrors the constitution's mandated Specification -> Plan -> Tasks -> Implementation sequence with a clear start and end, without presuming any future review/remediation-loop or Human Gate design.
- Q: What is the authoritative boundary for a feature's current workflow state? → A: A dedicated Workflow State Record colocated inside that feature's own spec-kit feature directory (alongside its `spec.md`/`plan.md`/`tasks.md`), distinct from those artifacts. This feature only reads that record; it defines no mechanism that creates or writes it. A feature directory that exists but has no such record is read as the initial state, `draft`.

### Session 2026-10-04 (Independent Implementation Review remediation)

- Q (I-1): How must the Workflow State Record's state member name be matched? → A: Exactly and case-sensitively. A member name that differs from the state member name only by letter case or case folding (for example `State`, `STATE`, `ſtate`) never represents the state field and makes the record `state_invalid`, even when an exact state member is also present; an exactly duplicated state member is also `state_invalid`. No last-key-wins resolution applies (human decision).
- Q (I-2): How must the feature identifier appear in human-readable reports? → A: Escaped and quoted (Go `%q` quoting) for every outcome of both capabilities, so that any identifier — including spaces, newlines, quotes, or backslashes — remains inside a single report line and cannot introduce an apparent outcome. The machine-readable format is unchanged (human decision).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Report the current workflow state of a feature (Priority: P1)

A developer or an automated caller wants to know, without applying or changing anything, which lifecycle phase a given feature is currently in.

**Why this priority**: This is the entire purpose of the feature: turning a feature's recorded (or default) condition into an observable, reportable Workflow State. Every other behavior in this feature exists to make this core answer trustworthy.

**Independent Test**: Can be fully tested by requesting the current Workflow State for a recognized feature — both one with no Workflow State Record and one with a record naming a specific canonical value — and confirming the report names exactly the expected state, reports whether it is terminal, and that nothing is written as a result.

**Acceptance Scenarios**:

1. **Given** a recognized feature with no Workflow State Record, **When** the developer requests its current Workflow State, **Then** `ai-dev` reports outcome `state_reported` with Workflow State `draft` and terminal `false`.
2. **Given** a recognized feature whose Workflow State Record names `planned`, **When** the developer requests its current Workflow State, **Then** `ai-dev` reports outcome `state_reported` with Workflow State `planned` and terminal `false`.
3. **Given** a recognized feature whose Workflow State Record names `approved`, **When** the developer requests its current Workflow State, **Then** `ai-dev` reports outcome `state_reported` with Workflow State `approved` and terminal `true`.
4. **Given** the same feature identifier and unchanged Workflow State Record content, **When** the developer repeats the identical request, **Then** the second report is identical to the first in outcome, Workflow State, and terminal flag.
5. **Given** a recognized feature, **When** the developer requests its current Workflow State in machine-readable mode, **Then** the machine-readable report exposes the feature identifier, the Workflow State value, the terminal flag, and the outcome value without requiring the reader to parse free-form text.
6. **Given** a completed request of any outcome, **When** the developer inspects the local repository and filesystem afterward, **Then** no content was created, modified, or deleted as a result of that request.

---

### User Story 2 - Evaluate whether a specific requested transition would be valid (Priority: P2)

A developer, or a future orchestration or Human Gate feature, wants to check whether moving a given feature from its current Workflow State to a specific candidate target state would be allowed — before anything actually applies that move.

**Why this priority**: Reporting current state alone does not tell a caller what moves are legal next. Establishing this check now, without any capability to apply it, gives later features (which will own applying transitions and Human Gates) a trustworthy, already-defined contract to build on, while keeping this feature strictly non-mutating.

**Independent Test**: Can be fully tested by requesting evaluation of a candidate target state against a recognized feature's current Workflow State — for a reachable target, an unreachable target, and a target outside the canonical vocabulary — and confirming each produces the correct, distinct outcome with no state ever written.

**Acceptance Scenarios**:

1. **Given** a feature currently in Workflow State `specified`, **When** the developer requests evaluation of candidate target `planned`, **Then** `ai-dev` reports outcome `transition_valid`.
2. **Given** a feature currently in Workflow State `specified`, **When** the developer requests evaluation of candidate target `tasked` (skipping `planned`), **Then** `ai-dev` reports outcome `transition_invalid`.
3. **Given** a feature currently in the terminal Workflow State `approved`, **When** the developer requests evaluation of any candidate target, **Then** `ai-dev` reports outcome `transition_invalid`, since no transition originates from a terminal state.
4. **Given** a feature currently in the terminal Workflow State `abandoned`, **When** the developer requests evaluation of any candidate target, **Then** `ai-dev` reports outcome `transition_invalid`, since no transition originates from a terminal state.
5. **Given** a feature currently in Workflow State `planned`, **When** the developer requests evaluation of candidate target `planned` (the same value as the current state), **Then** `ai-dev` reports outcome `transition_invalid`.
6. **Given** a feature currently in Workflow State `implemented`, **When** the developer requests evaluation of candidate target `specified` (a backward move, distinct from skipping ahead), **Then** `ai-dev` reports outcome `transition_invalid`.
7. **Given** a feature in any determinable Workflow State, **When** the developer requests evaluation of a candidate target value that is not one of the seven canonical Workflow State values (for example, `"reviewing"`), **Then** `ai-dev` reports outcome `target_unsupported`, reports the originally supplied value exactly as given, and performs no transition-rule lookup.
8. **Given** a feature identifier that does not correspond to any feature `ai-dev` recognizes as existing, together with a candidate target value that is not one of the seven canonical Workflow State values, **When** the developer requests a transition evaluation, **Then** `ai-dev` reports outcome `target_unsupported` rather than `feature_unknown`, and does not evaluate feature existence or read any Workflow State Record.
9. **Given** a recognized feature whose Workflow State Record is invalid or cannot be read (per FR-007), together with a candidate target value that is not one of the seven canonical Workflow State values, **When** the developer requests a transition evaluation, **Then** `ai-dev` reports outcome `target_unsupported` rather than `state_invalid`, and does not read or attempt to resolve the Workflow State Record.
10. **Given** any transition-evaluation outcome other than `transition_valid`, **When** the developer reads the report, **Then** it never resembles or could be mistaken for `transition_valid`, and the command reports unsuccessful completion.

### User Story 3 - Understand clearly when a feature or its recorded state cannot be determined (Priority: P3)

A developer or automated caller names a feature identifier that `ai-dev` does not recognize at all, or names a feature whose recorded Workflow State cannot be read as one of the canonical values, and needs to know immediately and unambiguously which of those two things happened, rather than receiving a guessed or defaulted answer.

**Why this priority**: Silently guessing a state, or conflating "no feature" with "no recorded state," would let a human or an automated caller act on a fabricated answer. This is prioritized after the core reporting and evaluation paths because it is a correctness guard on requests that never had a determinable state to begin with.

**Independent Test**: Can be fully tested by (a) requesting the current state or a transition evaluation for a feature identifier that does not correspond to any feature `ai-dev` recognizes, and (b) requesting the same for a recognized feature whose Workflow State Record content does not name one of the seven canonical values, and confirming each produces its own distinct, non-guessed outcome.

**Acceptance Scenarios**:

1. **Given** a feature identifier that does not correspond to any feature `ai-dev` recognizes as existing, **When** the developer requests its current Workflow State or a transition evaluation, **Then** `ai-dev` reports outcome `feature_unknown`, with no Workflow State and no transition result.
2. **Given** a recognized feature whose Workflow State Record cannot be matched to exactly one of the seven canonical Workflow State values under the exact, case-sensitive rule in FR-006 (for example, the record cannot be read because of a filesystem error, its state field is absent, empty, or whitespace-only, its content is otherwise unparseable, or it names an unrecognized or non-exact value), **When** the developer requests its current Workflow State, **Then** `ai-dev` reports outcome `state_invalid` rather than `draft` or any guessed canonical value, treated identically regardless of which of these conditions caused it.
3. **Given** the same feature described in Scenario 2, **When** the developer requests a transition evaluation for it, **Then** `ai-dev` reports outcome `state_invalid` rather than attempting a transition-rule lookup against a guessed current state.
4. **Given** any failure outcome (`feature_unknown`, `state_invalid`, `transition_invalid`, or `target_unsupported`), **When** the developer reads the report, **Then** it never resembles or could be mistaken for a success outcome (`state_reported` or `transition_valid`), and the command reports unsuccessful completion.

### Edge Cases

- What happens when no feature identifier is supplied at all? `ai-dev` reports a usage failure distinct from `feature_unknown`, emits no report for either capability, and completes unsuccessfully.
- What happens when the supplied feature identifier consists only of whitespace? `ai-dev` treats it as a missing identifier (a usage failure), not as `feature_unknown`.
- What happens when the transition-evaluation capability is requested with no candidate target value, or with more than one? `ai-dev` reports a usage failure, performs no lookup, emits no report, and completes unsuccessfully.
- What happens when a supplied candidate target value differs from a canonical Workflow State value only in letter case (for example, `"Planned"` instead of `"planned"`)? Matching is exact and case-sensitive; a non-matching case is reported as `target_unsupported`.
- What happens when a feature's Workflow State Record exists but its state field is absent, empty, or contains only whitespace? `ai-dev` reports `state_invalid` for both capabilities, exactly as it would for a non-canonical or unreadable record; none of these is treated as absence of the Workflow State Record, and none of them defaults to `draft`.
- What happens when a feature's Workflow State Record exists but cannot be opened or read because of a filesystem or I/O failure? `ai-dev` reports `state_invalid` for both capabilities, the same outcome as a malformed or non-canonical record; this is not a separate outcome and does not default to `draft`.
- What happens when a Workflow State Record's stored state value differs from a canonical Workflow State value only in letter case or leading/trailing whitespace (for example, `"Planned"` or `" planned "`)? Matching a record's state against the canonical values is exact and case-sensitive with no trimming or normalization (FR-006); any non-exact variation is `state_invalid`, not the corresponding canonical value.
- What happens when an unsupported output-format value is specified for either capability? `ai-dev` treats this as a usage failure under the same contract as any other usage failure (FR-020): no state determination, no Workflow State Record read, no Transition Rule Set lookup, no report emitted, no filesystem mutation, no coding agent discovery, selection, or execution, and unsuccessful completion.
- What is the overall evaluation order for a transition-evaluation request? Usage validation, then candidate-target canonicality, then feature existence, then Workflow State Record resolution and validation, then Transition Rule Set evaluation (FR-029). This fixed order applies only to the transition-evaluation capability; the state-reporting capability is unaffected and continues to evaluate only feature existence followed by Workflow State Record resolution.
- What happens when the transition-evaluation capability's candidate target is not one of the seven canonical Workflow State values and the feature identifier is also unrecognized? `ai-dev` reports `target_unsupported`, not `feature_unknown`; candidate-target canonicality is evaluated before feature existence (FR-029), so feature existence is never checked for this request.
- What happens when the transition-evaluation capability's candidate target is not one of the seven canonical Workflow State values and the feature's Workflow State Record is also invalid or unreadable? `ai-dev` reports `target_unsupported`, not `state_invalid`; candidate-target canonicality is evaluated before Workflow State Record resolution (FR-029), so the Workflow State Record is never read for this request.
- What happens when extra positional arguments or unrecognized options are supplied alongside an otherwise valid request? `ai-dev` reports a usage failure, invokes neither capability's logic, emits no report, and completes unsuccessfully.
- What happens when the same request is issued concurrently in multiple processes? Each request is independent; this specification does not require any coordination or locking between concurrent invocations.
- What happens when a Workflow State Record's content changes between two requests for the same feature? Each request reflects the Workflow State Record content at the time of that request; determinism (see Requirements) applies only when that content is unchanged between requests.
- What happens when a future feature adds a new Workflow State value or Transition Rule Set entry? Already-defined states and transitions are unaffected; the new value or entry behaves like any other once it exists.
- What happens when a future coding agent (002) or development role (003) is added? It has no effect on the Workflow State vocabulary, the Transition Rule Set, or the observable behavior of either capability defined here.
- What happens when a coding agent (002) reports that it completed its work successfully? That result is never treated as, or reported as equivalent to, a valid transition, a change of Workflow State, or authorization to advance to any other state; this feature's outcomes are entirely independent of any Coding Agent Execution Outcome.
- What happens when a development-role selection (003) resolves for a feature? It has no bearing on that feature's Workflow State, current or otherwise; role selection and workflow state remain entirely independent concepts.
- What happens to repository or filesystem content as a result of any request to either capability, regardless of outcome? Nothing is created, modified, or deleted; both capabilities are observational and read-only, and neither defines or performs the writing of a Workflow State Record.
- What happens when a feature is currently in a terminal Workflow State (`approved` or `abandoned`) and a transition to any target is evaluated? The result is always `transition_invalid`; this specification does not define any way to leave a terminal state.
- What happens when malformed syntax or options prevent `ai-dev` from recognizing a request to either capability? `ai-dev` reports a usage failure, leaves standard output empty of any state or transition report, and completes unsuccessfully; because no request was recognized, none of the defined outcomes applies.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST provide a capability to report the current Workflow State of exactly one explicitly identified feature, identified by that feature's feature identifier, with no other required argument.
- **FR-002**: The system MUST recognize exactly seven canonical Workflow State values: `draft`, `specified`, `planned`, `tasked`, `implemented`, `approved`, and `abandoned`. These values MUST be defined independently of any coding agent identity (002) or development role (003) and MUST NOT be expressed in terms of either.
- **FR-003**: `approved` and `abandoned` MUST be defined as terminal Workflow State values. The Transition Rule Set (FR-004) MUST NOT contain any entry whose origin is a terminal value.
- **FR-004**: The system MUST maintain the following fixed, built-in, deterministic Transition Rule Set of directed, single-step transitions between Workflow State values:

  | Origin | Allowed Target(s) |
  |---|---|
  | `draft` | `specified`, `abandoned` |
  | `specified` | `planned`, `abandoned` |
  | `planned` | `tasked`, `abandoned` |
  | `tasked` | `implemented`, `abandoned` |
  | `implemented` | `approved`, `abandoned` |
  | `approved` | *(none — terminal)* |
  | `abandoned` | *(none — terminal)* |

  No other origin-target pair is valid, including skipping ahead, moving backward, or a value transitioning to itself. The system MUST NOT provide any capability to view, edit, persist, override, score, or dynamically configure this Transition Rule Set within this feature.
- **FR-005**: When a supplied feature identifier resolves to a feature the system recognizes as existing, and that feature has no Workflow State Record, the system MUST treat that feature's current Workflow State as `draft` (the initial state) for both capabilities defined by this feature, rather than reporting an error or an undetermined state.
- **FR-006**: When a supplied feature identifier resolves to a recognized existing feature that has a Workflow State Record, the system MUST determine that feature's current Workflow State by matching the record's state value against the seven canonical Workflow State values (FR-002) exactly and case-sensitively. No trimming, normalization, aliasing, case folding, abbreviation, or other transformation MUST be applied to either the record's state value or the canonical values before this comparison. When, and only when, the record's state value matches a canonical value exactly under this rule, the system MUST treat that canonical value as the feature's current Workflow State for both capabilities.
- **FR-007**: When a recognized existing feature has a Workflow State Record but that record's state value does not match exactly one of the seven canonical Workflow State values under the rule in FR-006, the system MUST report outcome `state_invalid`, rather than defaulting to `draft`, guessing, or substituting any canonical value in its place. This single outcome applies uniformly, with no further distinction between them, to every one of the following conditions: the record cannot be opened, accessed, or read at all (for example, a filesystem or I/O failure); the record's content is structurally unparseable; the record's state field is absent; the record's state field is empty; the record's state field contains only whitespace; and the record's state field contains a value that is not one of the seven canonical Workflow State values, including a value that differs from a canonical value only in letter case, leading or trailing whitespace, or any other non-exact variation. None of these conditions is treated as absence of the Workflow State Record, and none of them produces `draft`; `draft` applies only when the Workflow State Record itself does not exist for an otherwise recognized feature, per FR-005. For the state-reporting capability, this rule is unconditional whenever the feature exists (FR-008 does not apply). For the transition-evaluation capability, this rule applies only after candidate-target canonicality (FR-011) and feature existence (FR-008) have each already failed to apply, per the fixed precedence order in FR-029; when the candidate target is not one of the seven canonical Workflow State values, this rule does not apply and the Workflow State Record MUST NOT be read, per FR-011.
- **FR-008**: When a supplied feature identifier does not resolve to any feature the system recognizes as existing, the system MUST report outcome `feature_unknown`, MUST NOT report any Workflow State value, and MUST NOT evaluate or report any transition result. For the state-reporting capability, this rule is unconditional. For the transition-evaluation capability, this rule applies only after candidate-target canonicality (FR-011) has already failed to apply, per the fixed precedence order in FR-029; when the candidate target is not one of the seven canonical Workflow State values, this rule does not apply, and the outcome is `target_unsupported` (FR-011) instead, regardless of whether the feature is recognized as existing.
- **FR-009**: For a recognized existing feature whose current Workflow State is determinable (FR-005 or FR-006), the state-reporting capability MUST report outcome `state_reported` together with the feature identifier, the current Workflow State value, and whether that value is terminal (FR-003).
- **FR-010**: The system MUST provide a second capability through which a human or automated caller supplies a feature identifier together with exactly one candidate target Workflow State value, and receives a report of whether the transition from that feature's current Workflow State to the candidate target would be valid under the Transition Rule Set (FR-004), without applying, persisting, recording, or otherwise causing that transition.
- **FR-011**: When the candidate target value supplied to the evaluation capability is not one of the seven canonical Workflow State values (FR-002), the system MUST report outcome `target_unsupported`, MUST report the originally supplied target value exactly as given, and MUST NOT report any canonical requested target or any transition result. This check takes precedence over every other transition-evaluation condition defined by this feature, per the fixed order in FR-029: the system MUST NOT evaluate feature existence (FR-008), MUST NOT read or otherwise attempt to resolve the Workflow State Record (FR-005, FR-006, FR-007), and MUST NOT perform any Transition Rule Set lookup (FR-012) — regardless of whether the identified feature exists or what its Workflow State Record, if any, contains.
- **FR-012**: When the candidate target value is one of the seven canonical Workflow State values and the feature's current Workflow State is determinable (FR-005 or FR-006), the system MUST report outcome `transition_valid` if and only if the Transition Rule Set (FR-004) contains a directed entry from the current Workflow State to that candidate target; otherwise it MUST report outcome `transition_invalid`. A candidate target equal to the feature's current Workflow State MUST report `transition_invalid`.
- **FR-013**: Every outcome the state-reporting capability reports for a recognized request MUST be exactly one of: `state_reported`, `feature_unknown`, or `state_invalid`. Every outcome the transition-evaluation capability reports for a recognized request MUST be exactly one of: `transition_valid`, `transition_invalid`, `target_unsupported`, `feature_unknown`, or `state_invalid`. No outcome may be ambiguous between these, and no failure outcome may be presented in a way that resembles or could be mistaken for `state_reported` or `transition_valid`.
- **FR-014**: The system MUST NOT create, modify, or delete any Workflow State Record, any other repository or filesystem content, or trigger any coding agent or role-selection action, as part of processing any request made to either capability defined by this feature, regardless of outcome. Both capabilities MUST remain strictly observational and read-only.
- **FR-015**: The system MUST NOT execute, launch, authenticate, or otherwise invoke any coding agent (002), and MUST NOT perform, trigger, or depend on any development-role selection (003), as part of processing any request made to either capability defined by this feature.
- **FR-016**: The system MUST NOT treat any Coding Agent Execution Outcome (002) or Role Selection Outcome (003) as input to, or an automatic trigger for, any Workflow State value, transition evaluation, or outcome reported by this feature. A coding agent reporting its own success, a role selection resolving successfully, or any implementation or review result MUST NOT, by itself, be treated as, or reported as equivalent to, Human Gate approval or authorization to transition a feature to any Workflow State — including, without limitation, the canonical `implemented` or `approved` Workflow State values. Reporting that a feature's current Workflow State is `approved` (FR-009) is strictly an observation of a value already present in that feature's Workflow State Record; this feature never infers, derives, grants, or authorizes that value, or any other Workflow State value, from a coding agent or role-selection outcome.
- **FR-017**: The system MUST require a separate, explicit request to report a Workflow State or to evaluate a transition. The system MUST NOT infer, perform, or trigger either capability as a side effect of any other capability, and MUST NOT independently decide that a feature's workflow has advanced, regressed, or otherwise changed.
- **FR-018**: For an identical feature identifier, identical Workflow State Record content (or its confirmed absence), an identical candidate target value where applicable, and an unchanged Transition Rule Set, the outcome and every reported value (current Workflow State, terminal flag, transition result) of both capabilities MUST be identical across repeated requests. The system MUST NOT use scoring, ranking, randomness, prompt-based inference, learning, or any other nondeterministic mechanism to determine or report a Workflow State or transition result.
- **FR-019**: The system MUST provide an explicitly selectable machine-readable report for both the state-reporting and transition-evaluation capabilities, in addition to a human-readable presentation, consistent with the pattern established by 002-coding-agent-execution and 003-agent-role-selection. For a recognized request in either machine-readable mode, standard output MUST contain exactly one final machine-readable report and no human-readable text. Every machine-readable report MUST include the feature identifier exactly as originally supplied and exactly one outcome value from FR-013, without requiring the reader to parse free-form text; both fields are always present regardless of outcome. Beyond those two always-present fields, each report MUST include exactly the fields required for its outcome and MUST NOT include any field prohibited for that outcome, per the following tables:

  **State-reporting capability**

  | Outcome | Workflow State value | Terminal flag |
  |---|---|---|
  | `state_reported` | REQUIRED | REQUIRED |
  | `feature_unknown` | PROHIBITED (absent) | PROHIBITED (absent) |
  | `state_invalid` | PROHIBITED (absent) | PROHIBITED (absent) |

  **Transition-evaluation capability**

  | Outcome | Current Workflow State value | Candidate target, exactly as supplied | Canonical candidate target |
  |---|---|---|---|
  | `transition_valid` | REQUIRED | REQUIRED | REQUIRED |
  | `transition_invalid` | REQUIRED | REQUIRED | REQUIRED |
  | `target_unsupported` | PROHIBITED (absent) | REQUIRED (per FR-011) | PROHIBITED (absent, per FR-011) |
  | `feature_unknown` | PROHIBITED (absent) | PROHIBITED (absent) | PROHIBITED (absent) |
  | `state_invalid` | PROHIBITED (absent) | PROHIBITED (absent) | PROHIBITED (absent) |

  No field beyond those named in these tables and the two always-present fields is defined by this feature; this requirement introduces no field not already named in the Key Entities section's Workflow State Report and Transition Evaluation Result.
- **FR-020**: When no feature identifier is supplied, when the supplied feature identifier consists only of whitespace, when the transition-evaluation capability is invoked with zero or more than one candidate target value, when an unsupported output-format value is specified for either capability, or when command syntax or options otherwise cannot be parsed into a recognized request, the system MUST treat this as a usage failure outside the outcome model defined by FR-013: it MUST report the usage problem, MUST NOT attempt any state determination, MUST NOT read any Workflow State Record, MUST NOT perform any Transition Rule Set lookup, MUST NOT emit a state or transition report, MUST NOT create, modify, or delete any Workflow State Record or other filesystem content, MUST NOT trigger any coding agent discovery, selection, or execution, and MUST complete unsuccessfully.
- **FR-021**: When the supplied candidate target value consists only of whitespace, the system MUST treat it as a missing target (a usage failure per FR-020), not as `target_unsupported`.
- **FR-022**: The command process reporting a request to either capability MUST report successful completion if and only if the outcome is `state_reported` (for the reporting capability) or `transition_valid` (for the evaluation capability), and MUST report unsuccessful completion for `feature_unknown`, `state_invalid`, `transition_invalid`, `target_unsupported`, or any usage failure. A usage failure's unsuccessful completion MUST occur without emitting any state or transition report.
- **FR-023**: The system MUST NOT introduce, append, or expose any credential, token, secret, or other sensitive environment value in any output either capability produces.
- **FR-024**: Adding a new coding agent to the supported-agent model (002) or a new development role to the recognized role model (003) MUST NOT require changing the Workflow State vocabulary (FR-002), the Transition Rule Set (FR-004), or the observable behavior of either capability defined by this feature.
- **FR-025**: Adding a new Workflow State value or Transition Rule Set entry in a future feature MUST NOT alter the reported outcome for any already-defined Workflow State or already-defined transition, given unchanged Workflow State Record content.
- **FR-026**: This feature MUST NOT change the approved observable behavior of the coding-agent listing or execution capabilities (002) or the role-selection capability (003); it MUST reuse, and MUST NOT redefine, their existing meanings of canonical agent identity, supported agent, local availability, development role, or role-selection outcome.
- **FR-027**: A feature's Workflow State Record, when one exists, MUST be located within that feature's own spec-kit feature directory, distinct from that feature's other spec-kit artifacts (for example, `spec.md`, `plan.md`, `tasks.md`). This feature defines that location as the sole authoritative source of that feature's current Workflow State for both capabilities. This feature does NOT define, and is not responsible for, any mechanism that creates, writes, or updates a Workflow State Record; a feature directory with no such record is read as `draft` per FR-005.
- **FR-028**: Every human-readable presentation of a recognized state-reporting or transition-evaluation result MUST visibly display the exact canonical outcome token produced for that request (one of the values listed in FR-013), for both the state-reporting capability and the transition-evaluation capability. This requirement governs only that the exact token is visibly present; it does not prescribe surrounding cosmetic formatting, except that each human-readable report MUST occupy exactly one line and MUST render the supplied feature identifier in escaped, quoted form for every outcome, so that no identifier can split the report across lines or present an apparent outcome other than the one actually produced (FR-013).
- **FR-029**: For a syntactically recognized transition-evaluation request, the system MUST evaluate conditions in exactly the following fixed order, stopping at and reporting the outcome of the first applicable step, and MUST NOT perform any later step's check or data access once an earlier step has already produced an outcome: (1) usage validation (FR-020, FR-021); (2) candidate-target canonicality (FR-011); (3) feature existence (FR-008); (4) Workflow State Record resolution and validation (FR-005, FR-006, FR-007); (5) Transition Rule Set evaluation (FR-012). This precedence governs only the transition-evaluation capability; it does not alter the state-reporting capability, which has no candidate target and is unaffected, continuing to evaluate only feature existence (FR-008) followed by Workflow State Record resolution (FR-005, FR-006, FR-007).

### Key Entities

- **Feature Identifier**: The value identifying which feature's Workflow State is being reported or evaluated, corresponding to that feature's spec-kit feature directory, independent of any coding agent identity or development role.
- **Workflow State**: One of a fixed enumeration of seven canonical values: `draft`, `specified`, `planned`, `tasked`, `implemented`, `approved`, `abandoned`. `approved` and `abandoned` are terminal; the other five are non-terminal.
- **Workflow State Record**: The authoritative representation of a feature's current Workflow State when one exists, located within that feature's own spec-kit feature directory and distinct from that feature's other spec-kit artifacts. Its state value is matched against the seven canonical Workflow State values exactly and case-sensitively, with no trimming, normalization, aliasing, case folding, or abbreviation (FR-006); a record whose state cannot be matched this way for any reason — including an absent, empty, or whitespace-only state field, an unreadable record, or a non-canonical value — is `state_invalid` (FR-007), which is distinct from the record's complete absence, which is `draft` (FR-005). This feature only reads it; no mechanism that creates or writes it is defined here.
- **Transition Rule Set**: The fixed, built-in, deterministic set of directed, single-step origin-to-target pairs between Workflow State values, defined in FR-004. Not human-viewable, editable, persistable, overridable, or dynamically configurable within this feature.
- **Workflow State Report**: The result of one state-reporting request: the feature identifier, the current Workflow State value (when determinable), whether it is terminal (when determinable), and exactly one outcome value (`state_reported`, `feature_unknown`, or `state_invalid`), presented in both human-readable and machine-readable form; the exact field-presence rule for each outcome is defined in FR-019, and the human-readable presentation's display requirement is defined in FR-028.
- **Transition Evaluation Request**: A feature identifier together with exactly one candidate target Workflow State value, supplied to check whether a transition from that feature's current state to that target would be valid, without applying it.
- **Transition Evaluation Result**: The result of one Transition Evaluation Request: the feature identifier, the current Workflow State value (when determinable), the candidate target value exactly as supplied, the canonical candidate target (when applicable), and exactly one outcome value (`transition_valid`, `transition_invalid`, `target_unsupported`, `feature_unknown`, or `state_invalid`), presented in both human-readable and machine-readable form; the exact field-presence rule for each outcome is defined in FR-019, the human-readable presentation's display requirement is defined in FR-028, and the fixed precedence governing which outcome is produced when more than one condition holds is defined in FR-029.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A developer or automated caller can determine, with a single request and without applying or changing anything, the current Workflow State of any recognized feature.
- **SC-002**: 100% of state-reporting requests for a recognized feature with no Workflow State Record report `draft`, with zero such requests reporting `feature_unknown` or `state_invalid` solely due to the record's absence.
- **SC-003**: 100% of transition-evaluation requests naming a candidate target value outside the seven canonical Workflow State values report `target_unsupported` — regardless of whether the identified feature exists or whether its Workflow State Record is valid — and 0% of them report `transition_valid`, `transition_invalid`, `feature_unknown`, or `state_invalid`; 0% of these requests result in the Workflow State Record being read.
- **SC-004**: 100% of transition-evaluation requests whose candidate target is not reachable from the feature's current Workflow State under the fixed Transition Rule Set report `transition_invalid` rather than `transition_valid`, including every terminal-state-origin case (both `approved` and `abandoned`), every skip-ahead case, every backward-move case, and every same-state case exercised by the acceptance scenarios.
- **SC-005**: 0% of requests to either capability, regardless of outcome, result in any Workflow State Record, repository, or filesystem content being created, modified, or deleted, or any coding agent or role-selection action being triggered.
- **SC-006**: An automated caller can determine, from the machine-readable report alone and without parsing free-form text, the feature identifier, the current Workflow State and its terminal flag when determinable, the candidate target value exactly as supplied when applicable, and the exact outcome value of any request to either capability.
- **SC-007**: Across fixtures for `state_reported`, `feature_unknown`, `state_invalid`, `transition_valid`, `transition_invalid`, and `target_unsupported`, 100% of completed requests report the expected outcome value, and the command reports successful completion if and only if the outcome is `state_reported` or `transition_valid`.
- **SC-008**: Adding a new coding agent (002) or a new development role (003) can occur without changing the reported outcome of any already-defined Workflow State or Transition Rule Set entry, given unchanged Workflow State Record content.
- **SC-009**: For an identical feature identifier, Workflow State Record content, candidate target value where applicable, and Transition Rule Set, 100% of repeated requests to either capability produce identical outcomes and reported values.
- **SC-010**: Across fixtures for an absent state field, an empty state field, a whitespace-only state field, a non-exact-case or whitespace-padded state value, a non-canonical state value, and an unreadable record, 100% of state-reporting and transition-evaluation requests for that feature report `state_invalid`, and 0% of them report `draft` or any other canonical Workflow State value.

## Assumptions

- A feature's Feature Identifier corresponds to that feature's spec-kit feature directory, consistent with the numbered `specs/<NNN-name>` convention already used by 001, 002, and 003, and independent of git branch naming.
- "Recognized as existing" means the system can locate that feature's spec-kit feature directory; this specification requires that recognition to be deterministic given unchanged repository content, but does not define the mechanism itself.
- A Workflow State Record, when present, is located within that feature's own spec-kit feature directory (the authoritative boundary established by this feature's clarification). This specification does not define its file name, serialization format, or schema beyond containing one of the seven canonical Workflow State values, and does not define any mechanism that creates, writes, or updates it — those are implementation-plan concerns and the responsibility of a future feature that will own applying transitions.
- A Workflow State Record's state value is matched against the seven canonical Workflow State values exactly and case-sensitively, with no trimming, normalization, aliasing, case folding, or abbreviation (FR-006). Any record whose state cannot be matched this way — including an absent, empty, whitespace-only, unreadable, or non-canonical state — produces `state_invalid` rather than `draft`; `draft` applies only when the Workflow State Record itself is completely absent for an otherwise recognized feature (FR-005, FR-007). This reflects an explicit remediation decision made after independent specification review.
- For the transition-evaluation capability, semantic evaluation precedence is fixed as: usage validation, then candidate-target canonicality, then feature existence, then Workflow State Record resolution and validation, then Transition Rule Set evaluation (FR-029). A non-canonical candidate target therefore always produces `target_unsupported` without the Workflow State Record ever being read, regardless of whether the identified feature exists or what its Workflow State Record contains. This precedence applies only to transition evaluation and does not change the state-reporting capability's order (feature existence, then Workflow State Record resolution). This reflects an explicit human product decision made after independent specification review.
- No mechanism defined by this feature ever writes, creates, or updates a Workflow State Record; a feature directory with no record present is read as `draft`, the initial state.
- Terminal states (`approved`, `abandoned`) admit no further transitions in the fixed Transition Rule Set. A future feature may define a capability to act on a terminal state (for example, re-opening a feature); this feature defines no such mechanism.
- This feature is strictly evaluate-and-report; it does not apply, persist, or record any transition, and introduces no capability to create, edit, override, or configure the Workflow State vocabulary or Transition Rule Set. This reflects an explicit human decision made during specification of this feature.
- Command syntax, programming language, CLI framework, and machine-readable serialization format are implementation/plan concerns, left open as long as the observable behavior defined here is satisfied, consistent with 002 and 003.
- This specification does not require or define any persistence of past reporting or evaluation requests between invocations; each request is independent.
- Coding Agent Execution Outcomes (002) and Role Selection Outcomes (003) remain entirely independent of this feature's outcomes; nothing in this feature derives a Workflow State, transition result, or outcome from either.
- This feature does not change the approved observable behavior of the existing coding-agent listing, coding-agent execution, or role-selection capabilities, and reuses rather than redefines their existing meanings of canonical agent identity, supported agent, local availability, and development role.
- This specification does not introduce or require any implementation-specific numeric exit code beyond what an existing, already-approved `ai-dev` compatibility contract requires.
