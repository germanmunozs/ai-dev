# Feature Specification: Coding Agent Execution

**Feature Branch**: `002-coding-agent-execution`

**Created**: 2026-09-27

**Status**: Draft

**Input**: User description: "Create the specification for the next AI Dev Orchestrator feature. Feature: Coding Agent Execution. The next capability is to introduce a vendor-neutral abstraction for discovering and invoking installed AI coding agents. Initially the system must support Claude Code and OpenAI Codex CLI. The purpose of this feature is execution, not intelligent agent routing. User goals: list supported coding agents and their local availability; explicitly select an agent and give it an instruction; ai-dev invokes the selected coding agent in the current project; the user receives the agent's result; failures are reported clearly and do not masquerade as successful runs; the design must permit additional coding-agent implementations later without changing the core agent execution model. Define observable behavior for commands conceptually equivalent to `ai-dev agents` and `ai-dev agent run <agent> <instruction>`, without assuming those exact names or syntax. Scope boundaries: no automatic agent selection, scoring, ranking, role-based routing, SDD workflow orchestration, multi-agent conversations, persistent workflow state, background execution, MCP orchestration, authentication management, usage/cost optimization, or Git commits/pull requests. Agent execution must remain explicitly initiated by the human; ai-dev must not silently elevate the selected coding agent's permissions or bypass its own approval/sandbox model; the specification must distinguish ai-dev execution failure from a coding agent's own unsuccessful result; no credentials, tokens, or secrets in output. Define the abstraction in vendor-neutral terms, leaving room for future agents without designing a plugin system now. Follow the project constitution."

## Clarifications

### Session 2026-09-27

- Q: Must the listing and/or execution capabilities provide an explicit machine-readable output mode for automated callers, similar to `ai-dev doctor`? → A: Yes, both capabilities MUST provide an explicitly selectable machine-readable report, consistent with the pattern established by `ai-dev doctor`.
- Q: How should the instruction text be supplied to the execution capability? → A: Support both a direct command argument and reading the instruction from standard input, to accommodate longer or multi-line instructions; a file-based mechanism is out of scope for this feature.
- Q: When a coding agent is invoked, how should its output reach the user? → A: Stream the agent's own output live as it runs, and additionally present one final, explicit outcome (success / agent-reported failure / ai-dev execution failure) once the invocation finishes, distinct from the streamed output itself.
- Q: When both a direct command argument and non-interactive standard input contain instruction text, what must `ai-dev` do? → A: Reject the request as ambiguous and do not invoke the agent.
- Q: What must the listing report when a supported agent is locally discoverable but has not been launched? → A: Report it as available; availability means locally discoverable at listing time and does not guarantee that a later launch will succeed.
- Q: In machine-readable execution mode, how must live agent output coexist with the final machine-readable report? → A: Reserve standard output exclusively for the final machine-readable report and stream all underlying-agent output through standard error.
- Q: Which stable identifiers must humans and automated callers use for the two initially supported agent implementations? → A: Use `claude-code` and `codex-cli` as immutable canonical identifiers, with display labels kept separate.
- Q: When no instruction argument is present, how must `ai-dev` treat standard input and empty content? → A: Read standard input only when it is non-interactive; reject zero-length or whitespace-only content as a missing instruction, and fail immediately when standard input is interactive.
- Q: Which exact stable values must the machine-readable execution report use for the three semantic outcomes? → A: Use `agent_succeeded`, `agent_failed`, and `execution_failed`.
- Q: When the human interrupts `ai-dev` during an active agent execution, what must happen to the agent process and reported outcome? → A: Forward cancellation, ensure the agent process stops before `ai-dev` exits, report `execution_failed` when reporting remains possible, and complete unsuccessfully.
- Q: How must malformed command syntax be distinguished from an `execution_failed` execution outcome? → A: Syntax and option-parsing errors that prevent recognition of an execution request are usage failures with no execution report; recognized requests that fail validation remain `execution_failed`.
- Q: In human-readable execution mode, how must agent stdout, agent stderr, and the final `ai-dev` outcome be routed and ordered? → A: Preserve agent stdout on stdout and agent stderr on stderr without labels, write the visibly delimited final `ai-dev` outcome to stderr, preserve order within each agent stream, and make no cross-stream ordering guarantee.
- Q: Which objective acceptance rule should define live streaming and unmistakable failure reporting? → A: Use a pre-exit marker test with a controllable blocking agent fixture, and require every final human outcome to display the exact canonical outcome value verified against the expected value and process completion status.

### Session 2026-11-20 (Amendment 1: the instruction is never an agent option)

The adapters ran `claude --print <instruction>` and `codex exec <instruction>`, so an instruction that starts with `-`, from either source, reached the agent as one of its options (for example `--dangerously-skip-permissions`). That broke FR-010 and the guarantees of FR-015 and FR-016.
- **Authority record.** German Munoz, repository owner, asked for this fix on 2026-11-20 in the words "si, apruebo la 010 y abre el bugfix". This is a declared, unauthenticated assertion.
- Q: How is the instruction passed? → A: As the last argument, immediately after an end-of-options marker `--`: `claude --print -- <instruction>` and `codex exec -- <instruction>`. The instruction text stays unmodified.
- **Subcommands.** Both CLIs have subcommands: `codex exec` has `review`, `resume`, `fork` and `help`, and `claude` has `doctor`, `install`, `mcp`, `auth` and others. Before this amendment, Codex CLI read an instruction equal to a subcommand name as that subcommand. After `--` it reads it as the prompt.
- **Verification with the real agents (2026-11-20, owner-authorized).** The CLIs were Codex CLI 0.166.0 and Claude Code 2.1.311, run in an empty temporary repository.
  - `ai-dev agent run codex-cli --version` and `… help` reached the model as prompts: tokens were used, and the model answered.
  - `ai-dev agent run claude-code --version`, `… help` and `… doctor` reached Claude Code's model path, which answered that the account had no usage credits. None of them printed a version, a help text or the `doctor` report.
  - `claude --print doctor`, without `--`, also took the model path. A static reading of Claude Code's bundled parser had suggested that a subcommand name could still be dispatched after `--`, but that was not reproduced.
- **Residual (codex-cli), accepted.** Codex CLI reads its prompt from standard input when the instruction is exactly `-`. Delivering every instruction through standard input was considered and declined, because it would take the interactive terminal away from the agent and need amendments to FR-005 and FR-016. On 2026-11-20 the owner chose to keep this as a documented limitation, in the words "déjalo documentado y sigue con el plan de la 010". This is a declared, unauthenticated assertion.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Discover which coding agents are available (Priority: P1)

A developer wants to know, before trying to use any coding agent through `ai-dev`, which coding agents `ai-dev` knows how to work with, and which of those are actually usable on their machine right now.

**Why this priority**: A user cannot make a valid, explicit choice of agent without first knowing what is supported and what is actually available. This is the entry point to every other capability in this feature.

**Independent Test**: Can be fully tested by running the listing capability on a machine where at least one supported agent is installed and at least one is not, and confirming the output names every supported agent and correctly reports each one's local availability.

**Acceptance Scenarios**:

1. **Given** a machine with Claude Code installed and discoverable and Codex CLI not installed, **When** the developer requests the list of coding agents, **Then** the output includes both Claude Code and Codex CLI, reports Claude Code as available, and reports Codex CLI as not available.
2. **Given** a machine with neither Claude Code nor Codex CLI installed, **When** the developer requests the list of coding agents, **Then** the output still names both supported agents and reports both as not available, without error.
3. **Given** a machine with both supported agents installed and discoverable, **When** the developer requests the list twice in a row without changing anything, **Then** both runs report identical results.

---

### User Story 2 - Run an explicitly chosen agent against an instruction (Priority: P2)

A developer who has decided which coding agent they want to use gives that agent, by name, a specific instruction to carry out in the current project, and wants to see what the agent did or produced.

**Why this priority**: This is the core value of the feature: turning a human decision ("use this agent for this task") into an actual invocation of that agent, with a visible result. It depends on User Story 1 only in the sense that a user should know the agent is available first, but it is independently testable on its own.

**Independent Test**: Can be fully tested by explicitly selecting an installed, available coding agent, supplying it an instruction, and confirming that the agent runs in the current project directory and that the user receives the agent's resulting output.

**Acceptance Scenarios**:

1. **Given** a supported coding agent that is installed and available, and a current project directory, **When** the developer explicitly selects that agent and supplies it an instruction as a command argument, **Then** `ai-dev` invokes that agent with that instruction against the current project, streams the agent's own output as it runs, and presents a final explicit outcome once the agent finishes.
2. **Given** the same setup, **When** the developer supplies the instruction via standard input instead of a command argument, **Then** the behavior is equivalent to supplying it as a command argument.
3. **Given** a supported coding agent that completes its work and reports its own success, **When** the invocation finishes, **Then** the final outcome presented to the user contains `agent_succeeded`.
4. **Given** a running invocation of a coding agent that itself prompts for approval or confirmation before taking an action, **When** that prompt occurs, **Then** `ai-dev` neither auto-approves nor suppresses that prompt, and the developer interacts with it exactly as they would running that agent directly.
5. **Given** an active coding agent invocation, **When** the developer interrupts `ai-dev` through an interruption it can handle, **Then** `ai-dev` forwards cancellation, ensures the agent process has stopped before exiting, reports `execution_failed`, and completes unsuccessfully.
6. **Given** an agent that writes distinguishable sequences to both standard output and standard error, **When** it runs in human-readable mode, **Then** each sequence appears unchanged and in order on its corresponding stream, the final `ai-dev` outcome appears as a separate final record on standard error, and no total ordering between the two streams is asserted.

---

### User Story 3 - Understand clearly why an execution attempt did not succeed (Priority: P3)

A developer whose attempt to run a coding agent did not produce a successful outcome — whether because `ai-dev` itself could not invoke the agent, or because the agent ran but reported its own unsuccessful result — wants to immediately understand which of those two things happened, without being told, or left to assume, that the run succeeded.

**Why this priority**: Silent or ambiguous failure reporting undermines trust in every other part of the feature; a user who cannot tell "ai-dev couldn't start the agent" from "the agent ran and failed on its own" cannot act correctly on the result. It is prioritized after the core execution flow because it is a quality property of that flow rather than a separate capability.

**Independent Test**: Can be fully tested by (a) selecting a supported agent that is not actually available and confirming a clear ai-dev-level failure is reported before any agent execution is attempted, and (b) selecting an available agent and supplying it an instruction that causes the agent itself to report failure, and confirming that failure is reported as the agent's own unsuccessful result rather than as an ai-dev failure or as a success.

**Acceptance Scenarios**:

1. **Given** a coding agent identifier that `ai-dev` does not support, **When** the developer requests execution with that identifier, **Then** `ai-dev` reports `execution_failed` with an explanation that the agent is unsupported, and does not attempt to invoke anything.
2. **Given** a supported coding agent that is not installed or not discoverable, **When** the developer requests execution with that agent, **Then** `ai-dev` reports `execution_failed` with an explanation that the agent is unavailable, before any invocation is attempted.
3. **Given** a supported, available coding agent that is invoked successfully by `ai-dev` but itself exits reporting that it did not complete the requested work, **When** the invocation finishes, **Then** `ai-dev` reports `agent_failed` rather than `execution_failed` or `agent_succeeded`.
4. **Given** any recognized execution request with a failure outcome, **When** the developer reads the final outcome, **Then** it contains exactly the expected failure value (`agent_failed` or `execution_failed`) and does not contain `agent_succeeded`.
5. **Given** command syntax or options that cannot be parsed into a recognized execution request, **When** the developer invokes the command, **Then** `ai-dev` reports a usage failure, invokes no agent, emits no execution report, and completes unsuccessfully.

---

### Edge Cases

- What happens when the developer selects an agent name that is not one of the agents `ai-dev` supports? Execution is refused with a clear, explicit "unsupported agent" failure; no invocation attempt is made (User Story 3, Scenario 1).
- What happens when the developer selects a supported agent that is not installed or not discoverable in the current environment? Execution is refused with a clear "agent unavailable" failure before any invocation attempt (User Story 3, Scenario 2).
- What happens when no instruction is supplied at all (neither as an argument nor via standard input)? `ai-dev` reports a clear failure that an instruction is required, and does not invoke the agent.
- What happens when no instruction argument is supplied and standard input is attached to an interactive terminal? `ai-dev` reports a missing-instruction failure immediately; it does not wait for terminal input and does not invoke the agent.
- What happens when the selected instruction source contains no characters or only whitespace? `ai-dev` treats the instruction as missing, reports a clear failure, and does not invoke the agent.
- What happens when both a direct command argument and standard input contain instruction text? `ai-dev` reports a clear failure that the instruction source is ambiguous and does not invoke the agent; it neither combines the sources nor silently ignores either source.
- What happens when the underlying coding agent process terminates unexpectedly (for example, it crashes or is killed) mid-run, rather than completing and reporting its own result? `ai-dev` reports this as an ai-dev-level execution failure (the agent did not run to completion), distinct from the agent's own reported unsuccessful result.
- What happens when the developer interrupts `ai-dev` during an active invocation? For an interruption `ai-dev` can handle, it forwards cancellation, ensures the agent process has stopped before exiting, reports `execution_failed` if it can still emit a final outcome, and completes unsuccessfully. No final-report guarantee applies when forced termination prevents `ai-dev` from running its interruption handling.
- What happens when an agent reported as available can no longer be found or its process cannot start when the developer explicitly requests execution? `ai-dev` reports an ai-dev execution failure; a prior availability result was only a point-in-time discovery result and did not guarantee successful launch.
- What happens when the coding agent itself requires the user to approve an action, authenticate, or otherwise interact with it during the run? `ai-dev` passes that interaction through to the user unchanged; it does not answer on the user's behalf and does not skip or suppress it.
- What happens when the current directory is not a valid project the coding agent can operate on (for example, outside any repository, if the agent requires one)? `ai-dev` invokes the agent as directed; if the agent itself refuses or fails for that reason, this is reported as the agent's own unsuccessful result, not an ai-dev execution failure, since ai-dev does not second-guess the agent's own operating requirements.
- What happens when the instruction text contains characters that could be misinterpreted (for example, quotes, newlines, or shell-significant characters)? The full instruction text supplied by the developer, exactly as given, is what reaches the coding agent; it is not truncated, reinterpreted, or partially applied.
- What happens when a coding agent's own output could contain a credential, token, or secret (for example, echoed from the agent's own logging)? This specification governs only what `ai-dev` itself adds to output; `ai-dev` MUST NOT itself introduce or append credentials, tokens, or secrets to any output it produces.
- What happens when arbitrary agent output resembles the machine-readable execution report? In machine-readable mode, it cannot corrupt or be mistaken for the report because all underlying-agent output is streamed through standard error and standard output contains only the final machine-readable report.
- What happens when agent standard output and standard error are produced concurrently in human-readable mode? Each native stream retains its own content and order, but their relative interleaving is unspecified; the final `ai-dev` outcome is a separate final record on standard error.
- What happens when malformed syntax or options prevent `ai-dev` from recognizing an execution request? `ai-dev` reports a usage failure on standard error, leaves standard output empty, invokes no agent, and completes unsuccessfully; because no execution request was recognized, none of the three execution outcomes applies.
- What happens when the developer runs the listing capability while a `ai-dev agent run`-equivalent invocation is already in progress in another process? Each is independent; this specification does not require any coordination or locking between concurrent invocations.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST provide a capability to list every coding agent `ai-dev` supports, with no required arguments.
- **FR-002**: For each supported coding agent, the listing MUST report whether that agent is currently available in the local environment in which `ai-dev` runs. For listing purposes, "available" means the agent is locally discoverable through the environment's standard executable lookup at the time of listing; it does not assert authentication, network reachability, or a guarantee that a later process launch will succeed.
- **FR-003**: The listing capability MUST report the same set of supported agents and the same availability result for each, given no change to the local environment between invocations.
- **FR-004**: The system MUST provide a capability through which a developer explicitly designates exactly one supported coding agent by its canonical identifier and supplies it a single instruction to execute. The same identifier MUST represent that agent in human-facing selection and machine-readable reports; a display label or executable filename is not an identifier.
- **FR-005**: The system MUST accept the instruction from exactly one of two sources: either a direct command argument or non-interactive standard input read through end-of-input. The resulting execution behavior MUST be equivalent regardless of which source was used. If both sources contain instruction text, the system MUST fail clearly, explain that the instruction source is ambiguous, and MUST NOT invoke the coding agent, combine the sources, or silently ignore either source. When no argument is present and standard input is interactive, the system MUST fail immediately rather than waiting for terminal input.
- **FR-006**: The system MUST require a separate, explicit user action to execute a coding agent; the system MUST NOT invoke any coding agent automatically, as a side effect of the listing capability, or as a side effect of any other command.
- **FR-007**: When execution is requested for a coding agent name that is not supported by `ai-dev`, the system MUST fail clearly, explain that the agent is unsupported, and MUST NOT attempt to invoke anything.
- **FR-008**: When execution is requested for a supported coding agent that is not currently available in the local environment, the system MUST fail clearly, explain that the agent is unavailable, and MUST NOT attempt to invoke that agent's process.
- **FR-009**: When execution is requested with no instruction supplied through either accepted mechanism, or when the selected source contains zero characters or only whitespace, the system MUST fail clearly, explain that an instruction is required, and MUST NOT invoke the coding agent. This validation MUST NOT otherwise modify non-empty instruction text before execution.
- **FR-010**: When a supported, available coding agent is invoked, the system MUST run it against the current project directory using exactly the instruction text supplied by the developer, unmodified. The instruction MUST be passed so that the agent's command-line parser cannot read it as one of its own options: as the last argument, after an end-of-options marker (Amendment 1, 2026-11-20), or, when verified for that agent, as the value attached to its prompt option within one argument *(Amended by Feature 013, A1)*.
- **FR-011**: While a coding agent invocation is running, the system MUST stream that agent's own output to the user as it is produced. "Live" means that when a controllable agent fixture writes and flushes a marker and then remains running until externally released, the marker becomes observable through `ai-dev` before the fixture is released or exits; no fixed elapsed-time threshold is required. In human-readable mode, agent standard output MUST be forwarded unchanged to standard output and agent standard error MUST be forwarded unchanged to standard error, without ai-dev labels inserted into either stream; production order MUST be preserved within each native stream, while relative ordering between the two streams is unspecified. In machine-readable execution mode, all underlying-agent output MUST instead be written to standard error, regardless of which native stream produced it; standard output MUST remain reserved for the final machine-readable report.
- **FR-012**: Upon completion of a coding agent invocation, in addition to the streamed output, the system MUST present a final, explicit ai-dev-authored outcome for that invocation, distinct from the underlying agent's output. In human-readable mode, this outcome MUST be a separate final record written to standard error, identify itself as the `ai-dev` outcome, and display exactly one canonical value from FR-013. In machine-readable execution mode, the final report MUST be the only content written to standard output.
- **FR-013**: Every final outcome the system presents for a recognized execution request MUST be exactly one of: (a) `agent_succeeded`, meaning the coding agent completed and reported its own success; (b) `agent_failed`, meaning the coding agent completed and reported its own unsuccessful result; or (c) `execution_failed`, meaning `ai-dev` rejected the recognized execution request or failed to start, supervise, or complete communication with the coding agent, distinct from any result the agent itself reported. Unsupported agents, unavailable agents, invalid or missing instructions, and process-start failures are `execution_failed`. These three stable semantic values MUST be used in machine-readable reports regardless of serialization format. No outcome may be ambiguous between them, and neither failure outcome may be presented in a way that resembles or could be mistaken for success.
- **FR-014**: Every `execution_failed` outcome MUST include a human-readable explanation distinguishing it from a coding agent's own reported result.
- **FR-015**: The system MUST NOT grant a selected coding agent any permission, capability, or credential beyond what that agent's own local installation already has; `ai-dev` MUST NOT elevate a coding agent's privileges as part of invoking it.
- **FR-016**: The system MUST preserve the selected coding agent's native approval and sandbox model. It MUST NOT bypass, auto-approve, suppress, or otherwise interfere with approval, confirmation, or sandboxing behavior; invoke the agent with an option, configuration, or environment change that relaxes those protections; or enable an unrestricted execution mode. Any interaction the agent surfaces MUST reach the developer unchanged.
- **FR-017**: The system MUST NOT introduce, append, or expose any credential, token, secret, or other sensitive environment value in the listing output, the agent's run output, or the final outcome that it itself produces.
- **FR-018**: Both the listing capability and the execution capability MUST each provide an explicitly selectable machine-readable report in addition to their human-readable presentation. The machine-readable listing report MUST expose, for every supported agent, its canonical identifier and exactly one stable availability value: `available` or `unavailable`. The machine-readable execution report MUST expose the requested agent identifier exactly as supplied and exactly one stable outcome value from FR-013: `agent_succeeded`, `agent_failed`, or `execution_failed`, without requiring the reader to parse free-form text. For a supported agent, the requested identifier is its canonical identifier; an unsupported identifier MUST NOT be represented as a supported Coding Agent. For a recognized request in either machine-readable mode, standard output MUST contain exactly one final machine-readable report and no human-readable text. During machine-readable execution, live underlying-agent output MUST stream through standard error.
- **FR-019**: The command process reporting an execution attempt MUST report successful completion if and only if the outcome is `agent_succeeded`, and MUST report unsuccessful completion for `agent_failed` or `execution_failed`.
- **FR-020**: The listing capability and the execution capability MUST interact with every supported coding agent through the same command syntax and interaction model; no user-facing behavior may require the developer to know or use agent-vendor-specific command syntax to list or run a given agent.
- **FR-021**: Adding support for an additional coding agent in the future MUST NOT require changing the observable command syntax, interaction model, or reported outcome structure of the listing or execution capabilities for already-supported agents.
- **FR-022**: The system MUST support, at minimum, Claude Code and OpenAI Codex CLI as coding agents that can appear in the listing and be selected for execution. Their immutable canonical identifiers MUST be `claude-code` and `codex-cli`, respectively. Human-readable display labels MAY be "Claude Code" and "OpenAI Codex CLI" but MUST NOT replace or alter those identifiers.
- **FR-023**: The system MUST NOT perform automatic agent selection, scoring, ranking, or role-based routing; the developer alone determines which supported agent is invoked for a given instruction.
- **FR-024**: One human-initiated execution request MUST target exactly one explicitly selected agent and produce at most one agent process invocation. The system MUST NOT automatically retry an agent, fall back to or retry through another agent, chain one agent execution into another, or continue the execution as a background task. A subsequent attempt requires a new explicit human action.
- **FR-025**: When `ai-dev` receives a human interruption that it can handle during an active agent invocation, it MUST forward cancellation to the agent, ensure the agent process has stopped before `ai-dev` exits, classify the outcome as `execution_failed`, and report unsuccessful process completion. It MUST emit the final outcome required by FR-012 when interruption handling still permits output. This requirement does not promise a final report when forced termination prevents `ai-dev` from executing its handler.
- **FR-026**: Syntax or option-parsing errors that prevent `ai-dev` from recognizing an execution request MUST be usage failures outside the execution-outcome model. For such a failure, `ai-dev` MUST invoke no agent, emit no execution report, leave standard output empty, report the usage problem on standard error, and complete unsuccessfully. Once an execution request is recognized, validation failures specified by FR-007 through FR-009 MUST instead produce `execution_failed`.

### Key Entities

- **Coding Agent**: A vendor-neutral representation of one AI coding agent implementation that `ai-dev` knows how to work with. Has an immutable canonical identifier used for human selection and machine-readable reporting, an optional human-readable display label, and a point-in-time local discovery state (`available` or `unavailable`) as defined by FR-002. Claude Code and Codex CLI are initial instances of this generic entity, not concepts in the core execution model. Additional coding agents can be represented without changing this definition.
- **Agent Listing**: The complete outcome of the listing capability for one invocation: every supported Coding Agent paired with its current availability state, presented in both human-readable and machine-readable form.
- **Execution Request**: A developer's explicit choice of exactly one supported Coding Agent plus the instruction text to give it.
- **Execution Outcome**: The result of one recognized execution request: the requested agent identifier, exactly one stable semantic value (`agent_succeeded`, `agent_failed`, or `execution_failed`), and any human-readable explanation associated with a failure, presented in both human-readable and machine-readable form. A supported requested identifier refers to its Coding Agent; an unsupported requested identifier does not create a Coding Agent entity.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A developer can determine, in a single command invocation, every coding agent `ai-dev` supports and which of those are usable on their machine right now, with no need to consult separate documentation.
- **SC-002**: 100% of listing invocations report an explicit availability result for every supported agent, with zero invocations producing a missing or ambiguous availability result.
- **SC-003**: A developer can go from deciding "use agent X for this instruction" to seeing agent X's result with exactly one explicit command, for every supported agent.
- **SC-004**: Across fixtures for agent success, agent-reported failure, unsupported agent, unavailable agent, missing or invalid instruction, process-start failure, unexpected process termination, and handled human interruption, 100% of completed final human outcomes display exactly the expected canonical value: `agent_succeeded`, `agent_failed`, or `execution_failed`.
- **SC-005**: Across every failure fixture listed in SC-004, 100% of final human and machine-readable outcomes contain the expected failure value (`agent_failed` or `execution_failed`), 0% contain `agent_succeeded`, and the command reports unsuccessful process completion.
- **SC-006**: An automated caller can determine, from the machine-readable reports alone and without parsing free-form text, every supported agent's availability and the exact outcome value of every recognized execution request.
- **SC-007**: Across every fixture listed in SC-004, an automated caller observes successful process completion if and only if the outcome is `agent_succeeded`, and unsuccessful process completion for every `agent_failed` or `execution_failed` outcome.
- **SC-008**: Support for a new coding agent can be added and verified against this specification's acceptance criteria without any of the existing acceptance scenarios for already-supported agents changing in observable behavior.
- **SC-009**: For fixtures that write and flush a distinct marker to each agent output stream and then block until externally released, 100% of markers are observable through the output destination required by FR-011 before the corresponding fixture is released or exits; order within each native stream matches production order.

## Assumptions

- "Supported" means `ai-dev` knows how to list and invoke the agent; it does not describe the local machine. "Installed and discoverable" / "available" means the agent can be located through the standard executable-lookup mechanism of the environment in which `ai-dev` runs at the time of the check. "Successfully executable" is established only when the agent process starts during a human-initiated execution request; listing does not launch an agent or guarantee later execution.
- Whether a coding agent is authenticated with its own AI service is out of scope for this feature's availability check, consistent with the Environment Doctor feature; "available" means the agent can be found, not that its process is guaranteed to start or that it can complete a request once started (an authentication failure surfaced by the agent itself produces `agent_failed`).
- "The current project" means the current working directory in which the `ai-dev` command is run; this specification does not define any project-selection mechanism beyond that.
- A single execution request targets exactly one coding agent and carries exactly one instruction; this specification does not define multi-agent invocation, conversation turns, or follow-up instructions within the same request.
- File-based instruction input (for example, reading the instruction from a named file) is out of scope for this feature; only a direct command argument and standard input are required.
- This specification does not require any persistence of past execution requests or outcomes between invocations; each invocation is independent.
- This specification does not require or define any Git operations (commits, branches, pull requests) as part of, or triggered by, agent execution.
- This specification intentionally leaves the choice of programming language, CLI framework, process-invocation approach, and machine-readable serialization format to the implementation plan.
- Coding-agent-specific behavior (for example, exact CLI flags, output formats, or exit-code conventions for Claude Code or Codex CLI) is an implementation concern for satisfying the vendor-neutral requirements above, not part of this specification.
